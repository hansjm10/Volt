# Content-Addressed Image Blobs and Binary Iroh Transfer

## Status

Proposed design.

This design is a coordinated breaking change for Volt and volt-app.

This design has no open architecture decisions. Section 22 contains release gates. A release gate can stop delivery. A release gate does not change the design.

## 1. Decision summary

Volt will use these rules:

1. The Volt agent directory will contain one global image blob store.
2. The blob store will keep the original encoded image bytes.
3. The blob store will address each blob with its SHA-256 digest.
4. Session JSON Lines (JSONL) files will keep blob references.
5. Session JSONL files will not keep base64 image data.
6. Agent state will keep blob references.
7. Agent state will not keep base64 image data.
8. Provider requests will get temporary base64 image data at the provider boundary.
9. Transcript frames will remain metadata-only.
10. The transcript projection will continue to publish `imageCount`.
11. The control plane will return image descriptors and scoped transfer grants.
12. The Iroh data plane will send raw blob bytes on dedicated bidirectional streams.
13. One blob stream will transfer one image.
14. The client will open each blob stream on the current shared Iroh connection.
15. A digest will identify data. A digest will not authorize data access.
16. Each transfer will bind to the current conversation authority.
17. Version 1 will not resume a partial transfer.
18. Version 1 will not multiplex blobs on one stream.
19. Version 1 will not compress blob bodies.
20. The app will keep a 24 MiB in-memory image cache.
21. The app will not add a durable blob cache in version 1.
22. Session format version 6 will replace inline images with blob references.
23. Iroh protocol `volt-rpc/1` will require the `conversation_blobs.v1` feature.
24. The coordinated release will remove the old base64 image recovery protocol.
25. The release will not include a base64 fallback.

The maximum original blob size will be 8 MiB. This limit is larger than the current 3 MiB app limit. The larger limit removes the current transport-driven restriction. Pixel and frame limits will still control decode cost.

## 2. Problem

Volt currently keeps base64 image data in `ImageContent.data`.

The current flow has these steps:

1. A local file, a remote prompt, a tool, or `image_gen` creates an `ImageContent` value.
2. Volt keeps the base64 string in agent state.
3. Volt writes the base64 string to session JSONL.
4. The transcript projection omits the image bytes and publishes `imageCount`.
5. The app calls `get_message_images` when an image row becomes visible.
6. The host puts the base64 string in a JSON response.
7. Iroh transports the complete JSONL record.
8. The app decodes the base64 string.

This flow has four problems.

First, base64 adds approximately one third to the encoded byte count. For example, a 2,366,562-byte PNG becomes a 3,155,416-byte base64 string.

Second, one Iroh JSONL record has a 4 MiB encoded limit. Iroh reads the stream in chunks, but the JSONL codec must buffer and parse the complete record. QUIC fragmentation does not remove the application record limit.

Third, the same image bytes can exist in a generated file, agent memory, session JSONL, an Iroh JSON response, and app memory.

Fourth, the current storage shape makes deduplication, independent transfer cancellation, and storage quotas difficult.

## 3. Existing behavior that this design preserves

The implementation MUST preserve these behaviors:

- The transcript projection MUST remain text-only.
- The transcript projection MUST publish a stable `imageCount`.
- The app MUST fetch image data only for visible transcript rows.
- The app MUST fetch an image again after a cold cache restore.
- The app MUST preserve image order in a message.
- The app MUST keep its current authority fences.
- The app MUST reject a late result from an old host, pool, transport, subscription, branch, session, entry, or operation.
- The app MUST keep the current 24 MiB retained-image least-recently-used cache.
- The host MUST preserve branch navigation and fork behavior.
- The host MUST preserve client-input write-ahead log (WAL) behavior.
- The host MUST preserve queued steering and follow-up inputs.
- The host MUST preserve pinned-agent close behavior.
- The host MUST preserve daemon and terminal user interface (TUI) lease transfer behavior.
- The host MUST preserve transcript bootstrap-before-tail ordering.
- The host MUST preserve transcript cursors, subscription identifiers, and branch epochs.
- The host MUST preserve provider image access.
- The `image_gen` tool MUST preserve the original generated bytes.
- The app MUST preserve the original downloaded bytes.

## 4. Goals

This design has these goals:

- Remove base64 image data from durable sessions.
- Remove image bodies from Iroh JSON.
- Keep the original encoded bytes without a transport conversion.
- Deduplicate identical image bytes.
- Keep transfer memory bounded.
- Keep decode work bounded.
- Keep storage use bounded.
- Keep transfer authorization scoped to one conversation authority.
- Make a stale transfer unable to publish data.
- Make a failed transfer safe to retry from byte zero.
- Make blob publication crash-safe.
- Make garbage collection safe for branches, forks, staged uploads, and active readers.
- Keep provider adapters independent from host storage.
- Keep local, tool, extension, generated, and remote image ingestion on one validation path.

## 5. Non-goals

Version 1 will not include these features:

- Partial transfer resumption.
- Chunk-level hashes.
- Multi-image streams.
- Peer-to-peer blob exchange between app devices.
- A durable app blob cache.
- A base64 compatibility mode.
- Animated images.
- Mutable project files as blob store objects.
- Blob body compression.
- Public blob URLs.
- Authorization by digest.

## 6. Controlled terms

This document uses these terms:

**BLOB**: The original encoded bytes for one validated image.

**DIGEST**: The lowercase hexadecimal SHA-256 value for a BLOB.

**BLOB REFERENCE**: Immutable metadata that identifies a BLOB.

**CONTENT-ADDRESSED STORE (CAS)**: The host store that uses a DIGEST as the object name.

**TRANSFER**: One upload or download on one Iroh bidirectional stream.

**DOWNLOAD GRANT**: A short-lived grant for one message image download.

**STAGED GRANT**: A short-lived grant for one uploaded image that a client input has not claimed.

**PIN**: A temporary reference that prevents garbage collection.

**CONVERSATION AUTHORITY**: The current identities and generations that permit a conversation operation.

**OWNER**: The process that owns the current conversation runtime. The OWNER is `voltd` or a TUI process.

The implementation MUST use these terms in protocol and storage code. It MUST not use a DIGEST as a synonym for a grant.

## 7. Architecture

The design has five layers.

### 7.1 Image ingestion

One importer will accept bytes from these sources:

- Local prompt files.
- Local Remote Procedure Call (RPC) input.
- App blob uploads.
- Image-reading tools.
- Extension-produced images.
- `image_gen` provider output.
- Session format version 5 migration.

The importer will validate the bytes. The importer will publish the BLOB to the CAS. The importer will return a BLOB REFERENCE.

### 7.2 Durable agent state

Session entries and in-memory agent messages will keep BLOB REFERENCE values. They will not keep base64 strings.

### 7.3 Provider materialization

The coding-agent package will resolve references immediately before a provider request. It will create an ephemeral provider message copy. Only this copy can contain base64 image data.

### 7.4 Transcript control plane

Transcript entries will continue to contain text and `imageCount`. The `get_message_image_refs` RPC command will return descriptors and DOWNLOAD GRANT values. It will not return image bytes.

### 7.5 Iroh data plane

The app will open a `conversationBlob` stream for one descriptor. The OWNER will send the raw BLOB body. The app will verify the body before it publishes an attachment.

The app will use the same authenticated Iroh connection as the conversation stream. This choice gives the host a direct connection-authority check. A blob timeout can retire this shared connection. Existing reconnect and bootstrap logic will restore the conversation.

## 8. Data model

### 8.1 Durable image content

Session format version 6 will use this shape:

```json
{
  "type": "image",
  "blob": {
    "algorithm": "sha256",
    "digest": "b7f0f4d0b0e3d4b3f0e6f8f3ec9a6fb57f5d8de8db264ab38c56f552e3e3f29c",
    "byteLength": 2366562
  },
  "mimeType": "image/png",
  "pixelWidth": 1536,
  "pixelHeight": 1024
}
```

The following rules are normative:

- `algorithm` MUST be `sha256`.
- `digest` MUST contain 64 lowercase hexadecimal characters.
- `digest` MUST be the SHA-256 value of the original BLOB bytes.
- `byteLength` MUST be a safe positive integer.
- `byteLength` MUST be 8 MiB or less.
- `mimeType` MUST come from byte inspection.
- `mimeType` MUST be `image/png`, `image/jpeg`, `image/webp`, or `image/gif`.
- `pixelWidth` and `pixelHeight` MUST come from byte inspection.
- Each dimension MUST be 4096 pixels or less.
- The product of the dimensions MUST be 16 megapixels or less.
- The image MUST contain exactly one frame.
- A content array MUST preserve image position and order.

The reference does not contain a file path. The reference does not contain base64 data.

### 8.2 Runtime type split

The implementation MUST separate stored image content from provider image content.

The agent layer will define a stored image type with the fields in section 8.1. User messages, tool results, custom messages, client-input WAL records, and queues will use this type.

The artificial intelligence (AI) provider layer will keep a provider-ready type:

```typescript
interface ProviderImageContent {
  type: "image";
  data: string;
  mimeType: string;
}
```

Only provider-ready messages can use `ProviderImageContent`.

The coding-agent materializer will convert stored image content to provider-ready image content. The low-level provider packages will not read the CAS.

This split prevents a session serializer from receiving provider base64 data by mistake.

### 8.3 Transcript descriptor

The control plane will use this descriptor:

```json
{
  "index": 0,
  "digest": "b7f0f4d0b0e3d4b3f0e6f8f3ec9a6fb57f5d8de8db264ab38c56f552e3e3f29c",
  "byteLength": 2366562,
  "mimeType": "image/png",
  "pixelWidth": 1536,
  "pixelHeight": 1024,
  "downloadGrant": "256-bit-random-base64url-value"
}
```

A descriptor is metadata. A `downloadGrant` is authority. A DIGEST is not authority.

## 9. Content-addressed store

### 9.1 Location

The default store will use this layout:

```text
~/.volt/agent/blobs/
  v1/
    sha256/
      b7/
        b7f0f4d0b0e3d4b3f0e6f8f3ec9a6fb57f5d8de8db264ab38c56f552e3e3f29c
    tmp/
    pins/
    trash/
    store.lock
```

The first two DIGEST characters select the shard directory.

The object file will not have a MIME-derived extension. MIME metadata belongs to the reference and to byte inspection.

### 9.2 File safety

The store MUST apply these rules:

- Store directories MUST have mode `0700`.
- Blob files MUST have mode `0600`.
- Temporary files MUST have mode `0600`.
- Pin files MUST have mode `0600`.
- The importer MUST reject a symbolic link.
- The importer MUST reject a non-regular file.
- The reader MUST open files without following symbolic links when the platform permits this operation.
- The reader MUST verify the opened file type.
- The store MUST not hard-link a mutable project file into the CAS.
- The store MUST not use an image file extension as validation.

### 9.3 Process ownership

The CAS is global to the Volt agent directory.

`voltd` is the remote authority and the garbage collection coordinator. A local TUI and a local RPC process MAY import or read a BLOB through the same process-safe store library. All processes MUST use the same lock and PIN rules.

### 9.4 Atomic publication

The importer will use this sequence:

1. Create a random temporary file on the CAS filesystem.
2. Stream bytes to the temporary file in chunks of 64 KiB or less.
3. Enforce the 8 MiB limit during the write.
4. Compute SHA-256 during the write.
5. Flush the temporary file.
6. Inspect the actual image format.
7. Inspect the frame count.
8. Inspect the dimensions.
9. Enforce the pixel limits.
10. Acquire `store.lock`.
11. Create a PIN for the new DIGEST.
12. Publish the temporary file with an atomic no-replace operation.
13. If the target exists, verify its file type, length, and DIGEST.
14. Flush the containing directory.
15. Release `store.lock`.
16. Return the BLOB REFERENCE and PIN.

The caller will write the durable reference after step 16. The caller will release the PIN only after the session entry or WAL record is durable.

The blob-first order is mandatory. A session entry MUST NOT refer to an unpublished BLOB.

A crash before the session write can create an orphan BLOB. Garbage collection will remove the orphan after the grace period.

### 9.5 Existing-object reuse

Deduplication is global in one agent directory.

The importer MUST verify an existing target before reuse. It MUST verify the regular-file type, byte length, and DIGEST. It MUST quarantine a corrupt target in `trash/`. It MUST fail the import after quarantine. A later import can create the correct object.

The store MUST not trust a file only because its name is a valid DIGEST.

## 10. Image validation

The host and the app will use equivalent validation rules.

A validator MUST:

1. Detect the format from the bytes.
2. Map the format to one canonical MIME type.
3. Reject a claimed MIME type that does not match the bytes.
4. Read the frame count.
5. Require exactly one frame.
6. Read the source dimensions without a full-size render when the image library permits this operation.
7. Require each dimension to be 4096 pixels or less.
8. Require the total pixel count to be 16 megapixels or less.
9. Reject malformed or truncated image data.
10. Reject extra container data when the format parser reports an invalid container.

The validator MUST reject animated GIF, animated WebP, and animated PNG data.

Validation does not change the BLOB. The CAS keeps the original bytes.

## 11. Image ingestion paths

### 11.1 Local prompt files

The prompt attachment code will stream each selected file to the importer. It will not first create a durable base64 value.

If image resize policy is necessary for a provider, section 13 will apply it to an ephemeral copy. The session will still refer to the original BLOB.

### 11.2 Image-reading tools

An image-reading tool will import the file before it returns the final tool result. The final tool result will contain a BLOB REFERENCE.

The tool MUST not keep base64 data in `details`, logs, or events.

### 11.3 Extensions

The extension API will expose an image import operation. The operation will accept a file path or bounded bytes. It will return stored image content.

An extension hook that replaces a user message or a tool result MUST return stored image content. It MUST not return provider image content.

This is a breaking extension API change. The coordinated release does not provide an inline-base64 compatibility path.

### 11.4 `image_gen`

The image provider can return `b64_json`. The tool will treat this value as transient input.

The tool will use this sequence:

1. Strictly decode the provider base64 value.
2. Enforce the 8 MiB decoded limit.
3. Validate the actual image.
4. Verify that the actual format is PNG when `image_gen` requires PNG output.
5. Write the requested `output_path` atomically.
6. Import the same original bytes into the CAS.
7. Return stored image content in the tool result.
8. Release all base64 references.

The CAS file and `output_path` are separate files. The tool MUST not hard-link them. A later user edit to `output_path` MUST not change the CAS object.

### 11.5 Remote app uploads

The app will upload the selected encoded bytes before it sends `prompt`, `steer`, or `follow_up`.

The app MUST not convert the image only to meet an Iroh JSON limit. The binary protocol has no image-body JSON limit.

The app MAY receive converted bytes from an operating-system picker. Those bytes become the upload source. Volt MUST not apply an additional persistent conversion.

## 12. Session format version 6

### 12.1 Scope

Version 6 will replace inline image data in these records:

- User messages.
- Tool-result messages.
- Custom messages.
- Client-input receipts.
- Client-input queued records.
- Any WAL payload that can replay an image-bearing input.

The migration MUST preserve:

- Session ID.
- Entry ID.
- Parent ID.
- Ordinal.
- Timestamp.
- Active leaf.
- Branch structure.
- Model state.
- Thinking state.
- Fast mode state.
- Client message ID.
- WAL identity.
- Queue order.
- Image order.
- Message semantics.

### 12.2 Migration procedure

The loader will use this procedure for a version 5 file:

1. Acquire the per-session migration lock.
2. Acquire the CAS store lock when an import requires it.
3. Read the source JSONL as a stream.
4. Parse each complete record with the current strict rules.
5. Find each inline image block.
6. Strictly decode its base64 data.
7. Validate the actual image bytes.
8. Import the BLOB.
9. Replace the inline block with a version 6 BLOB REFERENCE.
10. Write all records to a temporary version 6 JSONL file.
11. Flush the temporary file.
12. Atomically replace the version 5 file.
13. Flush the containing directory.
14. Release migration PIN values.
15. Release the locks.

The migration MUST be all-or-nothing for one session file.

If one image is corrupt, the migration MUST leave the version 5 file unchanged. The error MUST identify the entry ID and image index. The error MUST not print the base64 data.

A failed migration can leave unreferenced BLOB files. The grace period will protect and later collect these files.

### 12.3 Concurrent process rule

A process MUST hold the session lock before it opens a session for mutation. A version 5 process cannot coexist with a version 6 process for the same session.

An old binary already rejects a session version that is newer than its current version. This behavior prevents an old binary from rewriting a version 6 session.

### 12.4 In-memory sessions

An in-memory session will still import image bytes to the global CAS. It will hold PIN values until the session is disposed. This rule keeps agent messages reference-only.

## 13. Provider materialization

### 13.1 Boundary

The materializer will run after context transforms and before `convertToLlm` gives messages to a provider adapter.

The materializer will use this sequence:

1. Collect the stored image references in the selected context.
2. Enforce the aggregate materialization limits.
3. Acquire a reader PIN for each unique BLOB.
4. Open each CAS object as a private regular file.
5. Verify its length and DIGEST.
6. Verify its MIME type and image limits.
7. Create a provider-ready copy of the messages.
8. Create base64 data only in that copy.
9. Apply the existing provider resize policy to an ephemeral derivative when the provider requires it.
10. Call the existing provider conversion and request code.
11. Release file handles and PIN values after request payload construction.
12. Release all temporary base64 and derivative references.

The materializer MUST NOT write an ephemeral derivative to session JSONL. It MUST NOT publish an ephemeral derivative as the original CAS object. It MUST NOT put base64 data in logs, hooks, RPC frames, or transcript projections.

A missing or corrupt BLOB is a hard provider-call error. The materializer MUST not silently remove the image.

### 13.2 Provider limits

The original BLOB can be 8 MiB. A provider can have a smaller request limit.

The materializer MAY resize or re-encode an ephemeral provider copy. This operation does not change the original BLOB REFERENCE. It does not change transcript downloads.

The existing 2000-pixel provider resize policy and provider-specific encoded limits remain applicable to the ephemeral copy.

### 13.3 `blockImages`

The `blockImages` setting will replace stored image content with the existing text placeholder before the materializer reads any BLOB. This order prevents unnecessary file access and base64 allocation.

### 13.4 Recent images for `image_gen`

The `recentImages` provider for `image_gen` will collect BLOB REFERENCE values. It will materialize only the selected references. It will preserve the existing count and aggregate-byte limits.

## 14. Transcript metadata control plane

### 14.1 Transcript projection

The transcript projection will continue to publish `imageCount`. It will not publish a DIGEST, grant, path, or image body.

This rule keeps transcript frames small. It also keeps the app transcript cache metadata-only.

### 14.2 Descriptor command

The new command is `get_message_image_refs`.

Example request:

```json
  "entryId": "entry-id",
  "startImageIndex": 0

```

Example response data:

```json
{
  "workspaceName": "main",
  "sessionId": "session-id",

  "entryId": "entry-id",

    {
      "index": 0,

    }
  ],
  "nextImageIndex": 1

```

### 14.3 Paging rules

The host MUST apply these rules:

- One entry can advertise at most 64 images.
- One response page can contain at most 32 descriptors.
- The first image index MUST be zero.
- Indices MUST be contiguous in one page.
- Indices MUST be contiguous across pages.
- `totalImages` MUST remain stable for one subscription and branch epoch.
- The last index MUST be `totalImages - 1`.
- A subscription change MUST invalidate collected pages.
- A branch-epoch change MUST invalidate collected pages.
- The host MUST read references from the current active branch.
- The host MUST issue a separate DOWNLOAD GRANT for each descriptor.

A DOWNLOAD GRANT will contain 256 bits of random data. It will expire after 60 seconds. It will be single-use. The OWNER will keep at most 256 active download grants per client and conversation.

### 14.4 Removal of the old command

The coordinated activation will remove `get_message_images`. The schema and remote allowlist will not accept it.

## 15. Binary Iroh protocol

### 15.1 Protocol version

The coordinated release will change the Iroh application protocol to:

```text
volt-rpc/1
```

The host will advertise:

```text
conversation_blobs.v1
```

A compatible app MUST require this feature. A compatible host MUST require the app protocol epoch through the handshake `protocol` field.

### 15.2 Stream mode

The Iroh hello schema will add the `conversationBlob` mode.

A blob stream is an auxiliary stream. It MUST NOT enter `ConversationIngress`. It MUST NOT consume transcript sequence numbers. It MUST NOT change bootstrap-before-tail ordering.

The app will open one bidirectional stream for one TRANSFER. The app will use the same authenticated Iroh connection as the active conversation stream.

### 15.3 Common framing

The current Iroh hello line is the transfer header. The maximum encoded hello line remains 16 KiB.

All JSON headers MUST use UTF-8. Each header MUST end with one line-feed byte.

The parser MUST reject:

- Invalid UTF-8.
- Invalid JSON.
- Duplicate object members.
- Unknown fields.
- Missing required fields.
- Invalid safe integers.
- An unsupported protocol value.
- A header larger than 16 KiB.

The raw body starts immediately after the success header. A decoder MUST preserve body bytes that arrive in the same read as the final header byte.

A sender MUST write body chunks of 64 KiB or less. A receiver MUST keep no more than 64 KiB of unprocessed body data in memory.

A receiver MUST read exactly `byteLength` body bytes. It MUST then require stream FIN. It MUST reject early FIN. It MUST reject a missing FIN. It MUST reject trailing bytes.

A receiver MUST compute SHA-256 while it reads. It MUST compare the final value with `digest`.

A TRANSFER has a 10-second idle timeout. A TRANSFER has a 60-second total timeout.

Version 1 does not use body compression. Version 1 does not use offsets.

```json
  "clientNodeId": "client-node-id",
```

The client will then send exactly `byteLength` raw bytes and FIN.

```json
{

  "protocol": 1,
  "operation": "put",
  "status": "accepted",
  "stagedGrant": "256-bit-random-base64url-value",
  "digest": "b7f0f4d0b0e3d4b3f0e6f8f3ec9a6fb57f5d8de8db264ab38c56f552e3e3f29c",
  "byteLength": 2366562,
  "mimeType": "image/png",
  "pixelWidth": 1536,
  "pixelHeight": 1024
}
```

The STAGED GRANT will expire after 10 minutes. It will bind to the client node, Iroh connection, workspace, session, subscription, branch epoch, client message ID, image index, DIGEST, and byte length.

### 15.8 Prompt claim

The later `prompt`, `steer`, or `follow_up` command will contain staged image claims. It will not contain base64 data.

Example claim:

```json
{
  "index": 0,
  "stagedGrant": "256-bit-random-base64url-value",
  "digest": "b7f0f4d0b0e3d4b3f0e6f8f3ec9a6fb57f5d8de8db264ab38c56f552e3e3f29c",
  "byteLength": 2366562
}
```

Input admission will claim all staged grants in one transaction with the client-input WAL record. A partial claim MUST fail. A claimed grant MUST not authorize a second client message.

The existing client message ID idempotency rules remain authoritative. A replay of the same admitted client message MUST return the existing admission result. It MUST not append a duplicate input.

### 15.9 Transfer failure

Before a body starts, the host MAY send a structured failure handshake.

After a body starts, the failing endpoint will reset or close the stream. It MUST not send a JSON error after partial raw body data.

A retry will start at byte zero. A download retry requires a new DOWNLOAD GRANT. An upload retry can reuse an existing CAS object, but it requires a new STAGED GRANT.

## 16. Authorization

### 16.1 Capability rules

A download requires `conversation.observe.v1`.

An upload requires `conversation.control.v1`.

The existing static stream and RPC allowlists remain a hard ceiling.

### 16.2 Download authority

The OWNER will bind a DOWNLOAD GRANT to this tuple:

```text
clientNodeId
Iroh connectionId
workspaceName
sessionId
conversation owner generation
subscriptionId
branchEpoch
entryId
imageIndex
digest
byteLength
```

The OWNER MUST apply these checks before it sends the first body byte:

1. The Iroh client is authenticated.
2. The client grant revision is current.
3. An active conversation stream exists on the same Iroh connection.
4. The conversation stream has the same workspace and session.
5. The OWNER generation is current.
6. The subscription ID is current.
7. The branch epoch is current.
8. The entry is on the active branch.
9. The entry contains the image index.
10. The current reference matches the DIGEST and byte length.
11. The DOWNLOAD GRANT is current and unused.
12. Resource quotas permit the transfer.

The OWNER will consume the DOWNLOAD GRANT before body transfer. A failed transfer requires a new grant.

The OWNER MUST stop or fence a transfer when any authority in the tuple changes.

### 16.3 Upload authority

The OWNER will bind a STAGED GRANT to this tuple:

```text
clientNodeId
Iroh connectionId
workspaceName
sessionId
conversation owner generation
subscriptionId
branchEpoch
clientMessageId
imageIndex
digest
byteLength
```

The OWNER MUST revalidate this tuple when the prompt command claims the grant.

A staged upload is not a session reference. Garbage collection will retain it only through its PIN and grant lifetime.

### 16.4 Digest privacy rule

The host MUST return the same `blob_unavailable` error for an unknown BLOB and an unauthorized BLOB. This rule reduces existence probing.

The host MUST not list the global CAS. The host MUST not provide a fetch-by-DIGEST command.

## 17. TUI-owned conversations

A TUI can own the current conversation lease. In this state, the daemon authenticates the app, but the TUI owns the active branch and runtime.

The daemon MUST not authorize a blob from a stale view of the TUI branch.

The implementation will use this flow:

1. The app sends `get_message_image_refs` on the conversation stream.
2. The daemon relays that conversation stream to the TUI.
3. The TUI reads its active branch and creates DOWNLOAD GRANT values.
4. The app opens a sibling `conversationBlob` stream.
5. The daemon authenticates the stream and checks the active TUI lease.
6. The daemon creates a binary relay offer for the same TUI owner.
7. The daemon sends the authenticated client identity and physical connection identity in the relay preamble.
8. The TUI validates the grant and current branch.
9. The TUI reads the shared CAS and serves or receives the raw body.
10. The daemon copies bytes without JSON framing or inspection after the preamble.

The binary relay will reuse the existing byte-transparent relay transport. It will use a distinct relay kind. It will not invoke `runIrohRemoteRpcMode`.

A TUI lease change will close related blob relays. A closed blob relay will not close the session runtime.

For upload, the TUI will own the STAGED GRANT registry. The later relayed prompt command will claim the grant in the same TUI process.

## 18. App behavior

### 18.1 Lazy download

The app will use this sequence for a visible row:

1. Confirm that `remoteImageCount` is greater than zero.
2. Acquire the existing UIKit visibility lease.
3. Request descriptor pages on the conversation stream.
4. Validate workspace, session, subscription, branch epoch, entry ID, total count, and indices.
5. For each missing DIGEST, open one `conversationBlob` stream.
6. Stream the body to a protected temporary file.
7. Compute SHA-256 during the write.
8. Require exact length and FIN.
9. Validate the image with ImageIO.
10. Recheck the complete publication authority.
11. Read the validated original encoded bytes into the bounded memory cache.
12. Publish the attachment to the transcript item.
13. Delete the temporary file.

The app will not persist the downloaded BLOB in its transcript cache.

### 18.2 Cache and deduplication

The app will key retained BLOB data by DIGEST. It will keep the existing 24 MiB compressed-byte limit.

The app MAY reuse validated cached bytes for another descriptor with the same DIGEST. It MUST first receive an authorized descriptor for the target entry and index. A cache hit does not remove the authority check.

The app will coalesce concurrent requests for the same DIGEST. Version 1 allows only one active network blob transfer per app client.

The transcript item will preserve entry and index identity. The byte cache can use DIGEST identity.

### 18.3 Original bytes and rendering

The app will retain the original encoded BLOB bytes. It will not normalize or re-encode these retained bytes.

The app MAY create a transient thumbnail for display. The display path will keep the current 1600-pixel presentation bound. A thumbnail is not the original BLOB and is not a durable transcript artifact.

### 18.4 Temporary files

The app will store transfer files in a protected temporary directory. It will use complete-file protection when the platform permits it.

The app MUST delete transfer files after success, failure, cancellation, timeout, and authority loss. App startup MUST delete stale transfer files from earlier process exits.

### 18.5 Publication authority

The app will fence publication with this tuple:

```text
hostNodeId
pool lifecycle generation
transport generation
stream authority
subscriptionId
branchEpoch
workspaceName
sessionId
entryId
imageIndex
digest
operationId
```

The app MUST recheck this tuple after each asynchronous boundary. It MUST recheck it after final image validation. It MUST not publish a stale result.

## 19. Cancellation and native reads

### 19.1 Known constraint

The current Swift Iroh binding states that Swift task cancellation does not stop a pending native `RecvStream.read`. It also states that `RecvStream.stop` can wait for the same native read lock.

Therefore, `Task.cancel()` is not a physical cancellation mechanism.

### 19.2 Logical cancellation

When a row leaves the viewport, the app will revoke publication authority immediately. It will release the visibility lease immediately.

If a native read is pending, the app will let the single bounded transfer drain. The app will not start another blob transfer until that read settles.

This rule limits an abandoned native read to one per app pool.

### 19.3 Physical timeout

An independent timer will enforce the idle and total deadlines. The timer MUST NOT depend on completion of the pending read.

When a deadline expires, the app will:

1. Quarantine the exact pooled Iroh connection.
2. Revoke all conversation and blob generations that use that connection.
3. Close the physical connection.
4. Wait for the native read to settle.
5. Prevent reuse of the quarantined connection.
6. Reconnect through the existing pool lifecycle.
7. Run the normal conversation bootstrap and catch-up flow.

A timeout can interrupt a healthy sibling conversation stream. This is an accepted version 1 tradeoff. Existing reconnect behavior limits the user effect. A separate blob-only connection would add a second authorization and lifecycle domain.

### 19.4 Optional stream-local reset

The implementation MAY use a stream-local stop or reset only after the release-gate test proves all of these facts:

- A pending read returns in less than one second.
- A sibling conversation stream remains usable.
- A new sibling stream can open.
- Cancellation works during the header read.
- Cancellation works during the body read.
- Cancellation works during the FIN read.
- FIN and cancellation races do not hang.

If this proof fails, the implementation MUST use logical drain and physical connection retirement.

| Images per remote client input                     |             8 |
| Raw image bytes per remote client input            |        32 MiB |
| Materialized original bytes per provider request   |        50 MiB |
| App retained compressed bytes                      |        24 MiB |
| App active blob transfers                          |             1 |
| Host active blob transfers per client node         |             2 |
| Host active blob transfers globally                |            16 |
| Active download grants per client and conversation |           256 |
| Descriptor items per page                          |            32 |
| Staged blobs per client and conversation           |            32 |
| Staged bytes per client and conversation           |        32 MiB |

| Total transfer timeout                             |    60 seconds |
| Unreferenced BLOB grace period                     |      24 hours |

These blob stream limits are inside the daemon connection and global stream limits. A rejected blob stream MUST not create a runtime.

When the CAS exceeds the high watermark, `voltd` will:

1. Run garbage collection.
2. Permit a reference to an existing valid BLOB.
3. Reject a new unique BLOB if marked data remains above the high watermark.
4. Return `blob_store_full`.

Garbage collection MUST NOT delete a marked BLOB to reach the low target.

## 21. Pins and garbage collection

### 21.1 PIN rules

A PIN protects one DIGEST during a non-durable operation.

The store will create PIN files under `pins/`. A PIN file will contain a random owner identity, a DIGEST, an operation kind, a creation time, and an expiry time. It will not contain image bytes.

A process will create a PIN while it holds `store.lock`. A process will delete the PIN after the protected operation ends.

Transfer and materialization PIN values will expire after 5 minutes. Long migration operations MUST renew their PIN values before expiry.

A stale PIN cannot grant data access. It only delays deletion.

### 21.2 Mark set

Garbage collection will mark DIGEST values from:

- Every entry in every session tree.
- Inactive branches in each session file.
- Parent and forked session files.
- Custom-message image content.
- Client-input receipt records.
- Client-input queue records.
- Active STAGED GRANT values.
- Active transfer PIN values.
- Active provider-materialization PIN values.
- Active migration PIN values.

Storage retention follows the complete session tree. Remote download authority follows only the current active branch.

### 21.3 Collection procedure

`voltd` will use this sequence:

1. Acquire the global garbage collection lease.
2. Acquire `store.lock`.
3. Scan all authoritative session files.
4. Scan current PIN files.
5. Build the mark set.
6. If a session file is malformed, stop collection and delete nothing.
7. Ignore an unmarked BLOB that is younger than 24 hours.
8. Atomically move each eligible unmarked BLOB to `trash/`.
9. Release `store.lock`.
10. Delete trash files outside the lock.
11. Release the garbage collection lease.

The scanner MUST follow session references. It MUST not follow arbitrary filesystem paths from a session record.

The daemon will run collection at startup, once every 24 hours, and before it rejects a new BLOB for store exhaustion.

### 21.4 Reader race

A reader will acquire a PIN under `store.lock` before it opens a BLOB. Garbage collection will move only unpinned BLOB files while it holds the same lock. This sequence prevents deletion between authorization and open.

## 22. Failure model and release gates

### 22.1 Stable error codes

The control plane will use these stable codes:

| Code                     | Meaning                                                 |
| ------------------------ | ------------------------------------------------------- |
| `blob_invalid_request`   | A header or claim is malformed.                         |
| `blob_unavailable`       | The BLOB is unknown or the caller is not authorized.    |
| `blob_authority_stale`   | Conversation authority changed.                         |
| `blob_grant_expired`     | A transfer or staged grant expired.                     |
| `blob_busy`              | A concurrency quota rejected the transfer.              |
| `blob_too_large`         | A byte limit rejected the BLOB.                         |
| `blob_invalid_image`     | Image inspection rejected the bytes.                    |
| `blob_length_mismatch`   | The body length did not match the declaration.          |
| `blob_digest_mismatch`   | SHA-256 did not match the declaration.                  |
| `blob_timeout`           | An idle or total deadline expired.                      |
| `blob_store_full`        | No quota remains for a new unique BLOB.                 |
| `blob_stage_unavailable` | A staged claim is absent, stale, used, or unauthorized. |

After raw body transfer starts, the endpoint will use a generic stream reset. It will record the detailed local reason in bounded diagnostics.

### 22.2 Failure behavior

The implementation MUST apply these rules:

- A short body MUST fail.
- A body with trailing bytes MUST fail.
- A stalled body MUST fail.
- A wrong DIGEST MUST fail.
- A MIME mismatch MUST fail.
- A multi-frame image MUST fail.
- An oversized decoded image MUST fail.
- A stale OWNER completion MUST not publish.
- A stale app completion MUST not publish.
- A failed upload MUST not create a session reference.
- A failed session append MAY leave an orphan BLOB.
- A failed download MUST delete its temporary file.
- A connection replacement MUST invalidate all grants bound to the old connection.
- Access revocation MUST close active blob streams for that client.

### 22.3 Native cancellation release gate

The release MUST run an integration test against the exact pinned `iroh-ffi` revision.

The test MUST:

1. Keep a conversation stream active.
2. Block a blob read.
3. Cancel during each protocol phase.
4. Test a peer that never sends FIN.
5. Test trailing bytes.
6. Race FIN, cancellation, timeout, and connection replacement.
7. Repeat the race suite at least 1000 times.
8. Verify that no quarantined connection returns to the pool.
9. Verify that all native reads settle after physical connection close.
10. Verify that the app reconnects and receives a new conversation bootstrap.

Release is blocked if connection close cannot terminate the pending native read. Release is also blocked if a chosen stream-local reset harms a sibling stream.

### 22.4 No open design question

If stream-local reset fails the gate, version 1 will use shared-connection retirement. The implementation will not add a separate blob connection in this release.

## 23. Security considerations

### 23.1 Threats

The design addresses these threats:

- A client guesses a DIGEST from another session.
- A stale app transfer publishes after navigation.
- A stale OWNER serves data after lease transfer.
- A client replays a download grant.
- A client reuses a staged upload for another prompt.
- A client declares a small length and sends more bytes.
- A client declares a large length to reserve memory or disk.
- A peer stalls a native read.
- A malformed image causes excessive decode work.
- A symbolic link redirects a CAS read.
- Garbage collection deletes a live BLOB.
- A corrupt existing CAS file wins a deduplication race.

### 23.2 Required controls

The implementation MUST:

- Authenticate the Iroh node before transfer admission.
- Recheck the current grant revision.
- Require an active conversation on the same physical connection.
- Use random single-use transfer grants.
- Bind each grant to all conversation authority fields.
- Apply exact byte limits before allocation.
- Stream to disk instead of buffering an upload body.
- Validate frame and pixel limits.
- Use private files and directories.
- Use atomic publication.
- Use PIN values for active readers and staged uploads.
- Keep detailed transfer failures in host-local logs.
- Keep prompts, image bytes, base64 data, secrets, and full DIGEST values out of routine logs.

- Upload started.

## 28. Rejected alternatives

### 28.1 Keep base64 in JSON

This option keeps the one-third expansion. It also keeps the 4 MiB JSONL record restriction. It is rejected.

### 28.2 Put base64 text in the CAS

This option keeps the expansion. It addresses an encoding instead of the original bytes. It is rejected.

### 28.3 Split base64 across JSON chunks

This option adds application chunk state and keeps the expansion. QUIC already supplies ordered and reliable byte streams. It is rejected.

### 28.4 Put binary bodies on the conversation stream

This option mixes bulk data with cursor-ordered transcript traffic. It also weakens independent cancellation. It is rejected.

### 28.5 Use one stream for many images

This option creates cross-image head-of-line blocking. It also makes one cancellation affect unrelated images. It is rejected.

### 28.6 Use DIGEST values as capabilities

A client can learn a DIGEST from another context. Content identity is not access authority. This option is rejected.

### 28.7 Use reference counts as deletion authority

A process crash can make a mutable count incorrect. The session files and PIN values are the authoritative mark sources. This option is rejected.

### 28.8 Normalize images before durable storage

This option loses the original bytes. It can also change quality, metadata, alpha, and animation semantics. This option is rejected.

### 28.9 Use mutable output files as CAS objects

A user can edit an output file after generation. The bytes could then change under a stable DIGEST name. This option is rejected.

### 28.10 Add a durable app CAS in version 1

This option creates a second durable privacy, quota, migration, and garbage collection domain. The host CAS and app memory cache solve the current problem. This option is rejected.

### 28.11 Use a separate blob-only Iroh connection

This option isolates physical cancellation. It also adds a second connection authority, reconnect path, grant binding, and pool lifecycle. Version 1 will use the current shared connection and will retire it on a physical timeout. This option is rejected for version 1.

## 29. Acceptance criteria

The design is implemented when all of these statements are true:

- New session JSONL files contain no base64 image data.
- Migrated version 6 session JSONL files contain no base64 image data.
- In-memory agent state contains BLOB REFERENCE values.
- Provider base64 data exists only in ephemeral provider-ready copies.
- Transcript frames remain metadata-only.
- The app still starts image work from viewport visibility.
- `get_message_image_refs` returns no image bytes.
- Iroh JSON headers contain no image bodies.
- Iroh blob streams send the original raw bytes.
- The app verifies exact length, FIN, DIGEST, MIME type, frame count, and pixel limits.
- The host applies the same validation before CAS publication.
- The host never authorizes a download by DIGEST alone.
- A stale host or app authority cannot publish an image.
- Blob-first session persistence is crash-safe.
- Garbage collection preserves all session branches, forks, WAL records, staged grants, and active readers.
- The original `image_gen` bytes remain unchanged in the CAS and at `output_path` creation time.
- A provider resize does not change the stored original.
- The native cancellation release gate passes.
- The old `get_message_images` command is removed at activation.
- The release has no base64 fallback.
